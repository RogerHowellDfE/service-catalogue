# 0014. Credential-less by default: workload identity and federation before secrets

## Context

Every stored credential (password, client secret, API key, private key) can leak, expire unnoticed, or be copied somewhere it shouldn't be.
It also needs rotating and an owner. Azure, Entra ID and GitHub increasingly support identity-based access with no stored secret:
managed identities, workload identity federation and OIDC tokens. The cheapest secret to protect is one that doesn't exist.
It also helps the first-run experience: fewer things to configure.

## Decision

For every connection (app to service, CI to cloud, service to service), use the **first option in this order that works**:

1. **No credential needed**: a public, anonymous API (for example endoflife.date), or avoid the integration.
2. **Identity-based, with no stored secret**: managed identity (system-assigned by default), workload identity federation or OIDC. For example:
   - the app to **Azure Database for PostgreSQL** using Microsoft Entra authentication with the app's managed identity (Npgsql gets a token through Azure.Identity, or through the Aspire Azure Npgsql integration). Password authentication is turned off on the server.
   - the app to Key Vault, Storage and Monitor using managed identity
   - the Entra app registration for sign-in uses a **federated credential from the managed identity**, not a client secret or certificate
   - GitHub Actions to Azure through **OIDC federation** (`azure/login` with a client ID only). No Azure secrets are stored in GitHub
   - ADO through an Entra service principal or managed identity
3. **A key that never leaves a secure boundary**: for example a GitHub App private key held as a **non-exportable Key Vault key**, used to sign through the Key Vault API, so the key itself is never read by the app.
4. **Short-lived tokens obtained from 2 or 3**: for example GitHub App installation tokens, which expire after about an hour.
5. **A long-lived secret, as a last resort**: stored in Key Vault and read using managed identity. It must be declared (NFR-D6) with
   **why there's no credential-less option**, its minimum permissions, when it expires, and who rotates it. Examples: the GOV.UK Notify API key, and the GitHub personal access token used until M5.

**Locally**: the Aspire-managed PostgreSQL container's password is generated by Aspire and is never shared or committed. When local development uses
real Azure resources, `DefaultAzureCredential` signs in as the **developer's own identity** (Azure CLI or the IDE), so no shared service-principal secret is needed.
The per-integration choice is recorded in the [integration modes table](../architecture.md#integration-modes).

## Enforcement

- **Unit test**: every secret declaration (NFR-D6) has a non-empty "why no credential-less option", its minimum permissions, and an expiry and rotation note. Declarations at levels 1-4 don't need a secret at all.
- **Repository check** (checks CLI, [0012](0012-verification-checks-and-drift-detection.md)): configuration files (`appsettings*.json`, `launchSettings.json`, AppHost code) contain no `Password=`, `ClientSecret`, `AccountKey=`, `SharedAccessKey=` or private key blocks.
- **Workflow check**: `azure/login` steps use OIDC (`client-id`, with no `creds` or `client-secret`). Workflows only use `secrets.*` names on an allow-list, each linked to a declaration.
- **Secret scanning with push protection** on the repository.
- **Infrastructure as code policy (M4)**: PostgreSQL password authentication is disabled, Key Vault uses RBAC, and app registrations have no client secrets (Checkov or PSRule rules).
- These checks are also good candidates for **Insights checks across the estate** (for example "Azure login using a stored secret: review advised").

## Consequences

- Fewer secrets to set up, rotate and leak. Fewer support tickets when secrets expire.
- Managed identity and federation need Azure (and Entra tenant) permissions that may not be available within CIP or the DfE tenant. See U26.
- Local development against real Azure resources needs the developer to have suitable Azure RBAC roles.
- Failure mode: token acquisition fails (Entra unavailable, wrong role assignment). Health checks report it, and the error message names the identity and the role it's missing, never a secret.

## Alternatives considered

- Store everything in Key Vault and read it with managed identity: better than config files, but still long-lived secrets to rotate and leak. Kept only as the last resort (level 5).
- Client certificates for the app registration: better than secrets, but they still need rotating and storing. A federated credential needs neither.
